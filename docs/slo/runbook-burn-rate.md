# Burn-Rate Alert Runbook

This runbook covers alerts generated by `scripts/observability/evaluate_slo_burn_rate.py`.

## Alert severities

- `ok`: burn-rate below warning threshold.
- `warning`: error budget burn-rate is elevated and needs triage within one business day.
- `critical`: error budget burn-rate indicates active reliability risk; immediate response required.
- `no_data`: no telemetry sample in lookback window.

## Triage checklist

1. Confirm affected `use_case_id` and window in the report JSON.
2. Check if failures are concentrated by tenant, role, or adapter in `dimensions`.
3. Correlate with recent deploys, feature-flag changes, or staging chaos findings.
4. Verify if p95 latency regression and success-ratio regression are both present.

## Immediate actions

- For `critical` alerts:
  - page the owner listed in `use-case-slos.json`.
  - roll back recent risky toggles if available (`FEATURE_FLAG_*`).
  - if related to adapter health, execute the adapter chaos suite for confirmation.
- For `warning` alerts:
  - open an incident ticket and assign the owning team.
  - monitor two consecutive scheduled runs before closing.

## Escalation policy

- Two consecutive `critical` alerts for the same use-case require incident commander assignment.
- Three consecutive `warning` alerts require scheduling a reliability fix in the next sprint.

## Rollback and recovery notes

- If alert is tied to a newly rolled-out path, disable its feature flag first.
- Keep legacy path enabled until two consecutive `ok` runs are observed.
- Preserve generated evidence artifacts for at least 30 days.
